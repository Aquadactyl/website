## Browser load time

Headless Chromium, 1440x900, deviceScaleFactor 1, no CPU or network throttling, localhost Docker port forwarding. One warm-up pair discarded; ten measured pairs per panel in alternating order. Cold uses a new context restored from an authenticated session; warm reloads the same page/context. Server/OS caches remain warm. Wait for all 50 server names, then 2 seconds to observe paints. Third-party requests are blocked identically to isolate the local panel; blocked URLs are recorded. FCP/LCP are navigation-to-paint; dashboardReady is measured when all server names exist in DOM, a custom application milestone. Heap is CDP JSHeapUsedSize after an explicit garbage collection; not total browser RAM.

**Cold** means cold browser HTTP cache, with a pre-existing authenticated session. It does not mean a cold PHP process, database or OS cache. **Warm** is the next full-page reload in that context, with HTTP caching available. This measures the dashboard, not login or a client-side route transition. Login is outside all timings.

The dashboard-ready milestone uses animation-frame polling until all 50 fixture server names exist in the DOM, so it includes data fetching and rendering but has roughly one-frame observation granularity. It is not a standardized Time to Interactive or a field Core Web Vitals result. LCP is the latest candidate observed during the two-second settling window, not an unlimited observation of later page activity.

Each distribution renders its own dashboard layout and normal response fields. LCP candidates can therefore be different elements, and these tests compare the whole shipped page rather than an identical UI rewritten with two libraries.

## Authenticated API throughput

GET /api/client/account and GET /api/client?per_page=50, valid user API key, HTTP/1.1 persistent connections, uncompressed response bodies, concurrency 1/8/16; 10-second closed-loop windows, three repetitions with alternating panel order. Two-second warm-up before each run. No new requests after the window, in-flight requests drained and included in elapsed time. Validate every HTTP status and JSON result. Rate limits raised to 1,000,000/min on both disposable panels. Successes per actual elapsed second, not offered requests per second or a maximum capacity claim.

The **account** endpoint returns the fixture user's account; **servers** returns all 50 owned server records, including the panel's own server transformers and relationships. The server-list responses contain each distribution's normal fields, so response sizes differ. Neither endpoint contacts Wings. Results are endpoint-specific and do not describe file transfers, server power operations or every panel API.

Throughput is the median of three measured windows. Each p95 below is the median of the three per-window p95 values, not a percentile pooled across all requests. The raw report includes every successful request latency and all run durations, status counts and load-generator event-loop delays.

## Memory use

cgroup v2 memory.current minus inactive_file, clamped to zero (Docker-style working set). Separately retain raw usage bytes. Ten 1-second-spaced samples per window, three windows each after warm-up, idle and during concurrency-16 server-list load. Each sample records panel, database and Redis, and their sum. Peak is the maximum observed sample, not the kernel high-water mark. No application restarts or forced PHP GC between windows. Browser heap and server working set are different metrics.

The panel container includes nginx, supervisor, the FPM master and its four PHP workers, plus one queue worker. The **stack** column additionally includes that panel's separate MariaDB and Redis containers. It excludes Docker Desktop/WSL overhead, the load generator, browser and unrelated game containers. Library and OPcache pages shared among workers are accounted at container level, rather than adding process RSS values and double-counting shared pages.

| State  | Pterodactyl panel median | Aquadactyl panel median | Pterodactyl sampled panel peak | Aquadactyl sampled panel peak | Pterodactyl stack median | Aquadactyl stack median |
| ------ | ------------------------ | ----------------------- | ------------------------------ | ----------------------------- | ------------------------ | ----------------------- |
| idle   | 143.2 MiB                | 152.9 MiB               | 146.4 MiB                      | 157.8 MiB                     | 268.2 MiB                | 278.2 MiB               |
| loaded | 148.1 MiB                | 155.5 MiB               | 154.4 MiB                      | 156.5 MiB                     | 274.7 MiB                | 282.2 MiB               |

Each state has 30 samples per panel across three windows. Loaded samples use the authenticated 50-server-list endpoint at concurrency 16. The Docker working-set calculation follows [Docker's documented cache subtraction](https://docs.docker.com/reference/cli/docker/container/stats/). These are short steady-state observations, not a leak or long-running capacity test.

Aquadactyl's measured loaded container working set was higher (155.5 MiB versus 148.1 MiB); this is **not a memory improvement**. [Supplementary idle diagnostics](/benchmarks/panel-comparison-diagnostics.json), collected after the timed run, showed 82.5/82.9 MiB of anonymous memory in the previous/candidate Aquadactyl containers, but 0.9/24.9 MiB of active file cache and 3.3/7.3 MiB of reclaimable slab. Cache accounting dominates that before/after difference. Shared image pages and cgroup ownership limit container-memory comparisons; these observations do not establish a leak or a general RAM reduction.

Sampling pauses one second between collections; container-exec overhead adds to that interval. The raw report retains each sample timestamp. The helper shell and Docker sampling overhead are present for both panels.

## Reproduce

The commands below collect a **new two-way comparison** with the same fixture and resource limits. They do not recreate the original third Aquadactyl baseline or its alternating three-stack order. Keep the full three-way record and its measured runner when citing the published results.

Check out the exact source commits above. Apply the linked patch to Aquadactyl with git apply, then include --include-working-tree when preparing the stacks. Install each panel's locked dependencies and run its production frontend build (Aquadactyl: pnpm build; Pterodactyl: yarn build:production) before preparing the stacks. The [historical build comparison](/docs/panel/benchmarks#reproduce) describes asset collection separately. Build Aquadactyl's runtime image first (the test reuses its PHP extensions and OS packages for **both** panels), then run these commands from the website repository:

```bash
docker build -t aquadactyl:test /path/to/aquadactyl-bench
pnpm exec playwright install chromium
node scripts/prepare-runtime-benchmark.mjs /path/to/aquadactyl-bench /path/to/pterodactyl-bench --include-working-tree
```

The preparation script prints a temporary directory. Replace WORKDIR below with that path:

```bash
docker compose -f WORKDIR/compose.json up -d --build --wait --wait-timeout 240
node scripts/benchmark-runtime.mjs WORKDIR public/benchmarks/panel-comparison.json
node -e "require('fs').copyFileSync('WORKDIR/aquadactyl-source.patch', 'public/benchmarks/panel-comparison-aquadactyl.patch')"
node scripts/write-runtime-benchmark-guide.mjs panel-comparison
node scripts/verify-runtime-benchmark.mjs panel-comparison
docker compose -f WORKDIR/compose.json down --volumes
```

The generated Compose file binds only to 127.0.0.1:8091 and :8092 and has its own network, volumes and random disposable credentials. Never point this harness at a production database. The raw public report omits credentials and sessions. Keep its Composer lock hashes, image IDs and individual samples with any published comparison. The headline chart imports only the smaller summary, not the per-request latency arrays.
