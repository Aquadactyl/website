## Browser load time

Headless Chromium, 1440x900, deviceScaleFactor 1, no CPU or network throttling, localhost Docker port forwarding. One warm-up pair discarded; ten measured pairs per panel in rotating order. Cold uses a new context restored from an authenticated session; warm reloads the same page/context. Server/OS caches remain warm. Wait for the first visible fixture server row, then 2 seconds to observe paints. The dashboard uses each release's normal pagination; visible row counts are recorded. Third-party requests are blocked identically to isolate the local panel; blocked URLs are recorded. FCP/LCP are navigation-to-paint; dashboardReady is measured when a fixture server name first appears visibly in the viewport, a custom application milestone. Heap is CDP JSHeapUsedSize after an explicit garbage collection; not total browser RAM.

The milestone is the **first visible server-row link**, not Time to Interactive or completion of all server status calls. All three releases rendered 50 fixture rows in these runs; the raw samples retain rendered and viewport-visible row counts. Cold browser cache does not mean cold PHP, database or operating-system caches.

## Authenticated API

GET /api/client/account and GET /api/client?per_page=50, valid user API key, HTTP/1.1 persistent connections, uncompressed response bodies, concurrency 1/8/16; 10-second closed-loop windows, three repetitions with rotating panel order. Two-second warm-up before each run. No new requests after the window, in-flight requests drained and included in elapsed time. Validate every HTTP status and JSON result. Rate limits raised to 1,000,000/min on all three disposable panels. Successes per actual elapsed second, not offered requests per second or a maximum capacity claim.

Each row reports the median of three window rates and the median of three per-window p95 latencies. These are not pooled percentiles. Every measured request returned a valid successful response.

## Server memory

cgroup v2 memory.current minus inactive_file, clamped to zero (Docker-style working set). Separately retain raw usage bytes. Ten 1-second-spaced samples per window, three windows each after warm-up, idle and during concurrency-16 server-list load. Each sample records panel, database and Redis, and their sum. Peak is the maximum observed sample, not the kernel high-water mark. No application restarts or forced PHP GC between windows. Browser heap and server working set are different metrics.

## Limits and history

Single shared Windows/WSL2 workstation; existing unrelated application containers remain running. No CPU pinning, controlled network emulation, TLS, WAN latency, mobile device, endurance test or real-player load. This is a controlled local configuration comparison of pinned distributions, not their default deployment presets or proof of general production capacity.

The host was Intel(R) Core(TM) i7-14700KF, 28 logical CPUs and 64 GiB RAM, running Docker 29.8.1 on WSL2. Chromium 156.0.8078.4; Playwright 1.64.1. Source, runtime image, lockfile, configuration and asset hashes accompany the samples. No general production capacity claim is made.

October's [Panel v1 data](/benchmarks/panel-comparison.json), [Panel v2 beta 2 data](/benchmarks/panel-v2-comparison.json) and [older runtime comparison](/docs/panel/runtime-benchmarks) remain available as historical evidence. Their versions, environments and readiness rules differ; do not treat changes between dates as a controlled optimization experiment.
