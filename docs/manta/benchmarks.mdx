## API throughput and latency

Three repetitions alternate daemon order. Each endpoint/concurrency combination sends 400 authenticated HTTP requests using persistent connections at concurrency 1, 16 or 32. The client runs inside Docker on the shared local network, with a 4-core quota and 1 GiB memory limit. These short closed-loop batches report observed throughput, not sustained production capacity. Panel and daemon benchmark workloads ran separately.

Throughput is the median of three batch rates. The p50/p95 columns are medians of three per-batch percentiles, not pooled percentiles. Lower latency and higher throughput are preferable. 14,400 timed API requests completed with **0 errors**.

## Memory use

One approximately 30-second idle window and one approximately 30-second command-load window, with 15 Docker working-set samples per container per window. Values are arithmetic means of those samples, **not medians or process RSS**. Working set is container usage minus inactive file cache; the raw result retains sampled peaks and CPU observations. Daemon memory excludes its game containers, Panel, database, Redis and host overhead. No forced garbage collection occurs between workloads.

The command workload alternates a 4,096-block area between stone and air at five commands per second per game, using matching forced/ticking areas. Java/Bedrock status queries occur while the workload remains active; these are not player latency measurements.

## Isolated Manta measurements

A separate run repeated 31 isolated cases five times each with a 500 ms target per sample, using Go 1.26.9 Linux amd64, a 4-core quota, 2 GiB memory and `GOMAXPROCS=4`. It covers Docker stats decoding, console inspection, UUID lookup, resource-event handling, directory encoding, file streaming, API routing, WebSocket encoding, request bodies and ready event sinks. [Every timing/allocation sample](/benchmarks/daemon-microbenchmarks.txt) is retained. These are current Manta measurements; they do not supply a new isolated Wings baseline or establish game TPS/player capacity. They ran separately from the live comparison and test suite.

## Resource-event delivery

The automatic stats check connected 16 authenticated WebSocket viewers to each of the four benchmark games. All 64 viewers received three unsolicited stats samples each (192 samples total), with the expected API fields, valid counters and advancing uptime. This checks the periodic event path rather than requested `send stats` replies; it is a correctness check, not a player-capacity measurement. Per-viewer observations are retained in the raw report.

## Tests and coverage

The Manta verification run passed **823 Go cases/subtests in 28 packages** with the race detector; 0 failures and 0 skips. Go vet passed. Tests used go version go1.26.9 linux/amd64 against an isolated Docker engine; the production compiler is recorded above.

Statement coverage is **91.70% (7,565 of 8,250 statements)** across all Go packages, including the CLI and benchmark runner. **The 100% statement-coverage target is not met: 685 statements remain uncovered.** No source files were excluded to raise the percentage. Passing the full suite is separate from reaching full statement coverage.

[Coverage counts and uncovered blocks](/benchmarks/daemon-coverage.json) · [Unfiltered Go coverage profile, gzip](/benchmarks/daemon-coverage.out.gz). The profile was collected with `go test -race -coverpkg=./... -covermode=atomic -coverprofile=coverage.out ./...`; the report records exact counts and hashes. Manta's `benchmarks/coverage_report.py` checks the exact 100% threshold and exits nonzero while any statements remain uncovered.

## Reproduce and limits

Host: Intel(R) Core(TM) i7-14700KF; 64 GiB RAM; win32 10.0.26300 x64. Shared Windows/WSL2 Docker workstation, existing unrelated containers running, no CPU pinning, WAN/TLS emulation, real players or endurance load. Results depend on configuration, workload and the short observation windows. They cannot establish a universal speed-up or an overall performance score.

Use the exact source/image/binary hashes in the raw report. The linked Manta patch and measured runner source record the local changes. The existing dedicated stack and cached game installations were provisioned with the Manta repository's benchmarks/provision.php; its README documents the local node setup and manifest guards. It is not a fresh-machine deployment recipe. The full run starts/stops only those four benchmark servers and writes fixtures under their bench directories.

From the Manta checkout, with the dedicated stack prepared and matching CPU/memory overrides applied:

```powershell
.\benchmarks\Run-Benchmark.ps1 -Phases lifecycle,performance,resources,security -OutputDirectory C:\path\to\fresh-results
```

Keep the private manifest out of published artifacts. The runner creates a temporary credential file and removes it after the run.
