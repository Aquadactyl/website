Measured **2026-11-22**: **Manta v1.3-beta** versus **Wings v1.13.5**, compiled from unmodified release tags with Go 1.27.4 and matching build flags. Both use the same runtime image and resource limits. The homepage shows three fixed metrics; all measured workloads, including regressions, appear here.

Unmodified tagged source, identical Go 1.27.4 compiler/build flags and common Alpine runtime image. Each daemon has a two-core quota, 1 GiB RAM, GOMAXPROCS=2. Games have matching pinned images and configured limits. Private nested Docker engine is limited to 16 cores/12 GiB and publishes no host ports. Manta uses Aquadactyl; stock Wings uses its native Pterodactyl v1 backend (Wings page=0 bootstrap is incompatible with Aquadactyl validation). No production-code compatibility patch is applied. Panel and daemon workloads do not overlap.

Both executables are rebuilt from released source, rather than comparing a custom Manta binary to an upstream prebuilt Wings image. Binary and Go dependency hashes, runtime image IDs and effective game-container limits are recorded. The native backend pairing avoids changing stock Wings' zero-based bootstrap pagination. HTTP/file timings call the daemon directly; SFTP authentication and bootstrap are not part of transfer timers.

The host is Intel(R) Core(TM) i7-14700KF, 28 logical CPUs and 64 GiB RAM. The private engine is Docker 29.8.1; the load generator has four CPU cores and 1 GiB RAM. Existing unrelated workstation containers remain running.

## Matching game fixtures

Each daemon manages one **Paper 26.3 build 257** server and one **Bedrock 1.26.66.1** server. The same downloaded bytes and image digests are used on both sides. Paper has 1536 MiB configured memory and Bedrock 512 MiB; both have a 200% CPU limit. Effective cgroup memory includes the daemons' normal overhead allowance and is checked for parity. Both use the same seed and properties apart from assigned ports. No authenticated players or bots participated.

Four start/stop rounds per game and daemon in alternating order. Fresh worlds are initialized by the first start, which is retained as a discarded warm-up; only the next three warm starts contribute to the published lifecycle medians. Timers cover power request through daemon-reported state, with 100 ms polling; shutdown is not a separately timed OS process exit. Identical cached binaries/image layers, seed and properties; normal configuration sync and registry digest checks remain in the timed power path. Bedrock explicitly uses transport=raknet for the UDP query workload.

## API throughput and latency

Three alternating repetitions per daemon, endpoint and concurrency (1/16/32). Five-second closed-loop authenticated HTTP/1.1 windows with persistent connections; one discarded request before each window. No new requests after the deadline; in-flight requests are drained. Throughput is successful requests per actual elapsed second. Body receipt is included, percentile sorting and publication are excluded. Timed responses must be HTTP 200. This replaces the old 400-request batches; do not claim a controlled before/after comparison across methods.

Throughput is the median of three per-window rates. The p50/p95 columns are medians of the per-window percentiles, not pooled percentiles. The measured runner uses the lower middle order statistic for p50 and floor((n−1)×0.95) for p95. All 4,654,944 measured API requests completed with **zero errors**. The directory size and running server state are checked outside each timed window.

## Memory and command load

Fifteen Docker working-set samples at two-second intervals for each of six containers, once idle and once under matching game command load. Mean is arithmetic mean; raw sample values and observed peaks are retained. Working set subtracts inactive file cache, not RSS. Commands alternate 4096 blocks between stone and air, five iterations/second per node across both games, with matching forced/ticking areas. This is not real-player load.

Daemon memory excludes game containers, Panel, database, Redis and host overhead. No forced daemon GC occurs between workloads. The command workload is synthetic and deliberately small; these figures are not a player-capacity benchmark.

## Reproduction and limitations

The website repository contains the exact guarded [setup, provisioning and workload sources](https://github.com/Aquadactyl/website/tree/main/scripts/daemon-suite). Follow its README with clean tagged checkouts and fresh disposable databases. Game binaries are downloaded from their publishers and are not redistributed with the report. Private account passwords, node tokens and configuration files are excluded from public artifacts.

Single shared Windows/WSL2 workstation with unrelated existing containers, no CPU pinning or repeated clean-machine trials. Linux container networking; no TLS/WAN/mobile/endurance test or authenticated players. Daemon and game memory are separate; this is a controlled local distribution comparison, not general hosting capacity. No new security audit, race test or full coverage run is claimed by this performance rerun.

[November 2 results](/benchmarks/daemon-comparison.json), [its historical Manta source patch](/benchmarks/daemon-comparison-manta.patch), [coverage report](/benchmarks/daemon-coverage.json) and [microbenchmarks](/benchmarks/daemon-microbenchmarks.txt) remain available. Those security/coverage/microbenchmark runs were **not repeated** as part of this current-release performance comparison. Older 400-request API batches and existing worlds differ from this rerun; do not present differences across dates as a controlled optimization experiment.

## v1.3-beta directory-listing follow-up

Manta v1.3-beta includes a separate component optimization measured on **22 November
2026** against revision **80f84fbda9a7513c995d5a0456085df5adcd9c71**. Metadata is
collected relative to the open directory descriptor, avoiding repeated parent-path
traversal while retaining root-confined, nonblocking MIME inspection.

| Component case                        |    Before |    After | Time reduction |
| ------------------------------------- | --------: | -------: | -------------: |
| 1,000 regular files, root read        |  5.250 ms | 4.395 ms |          16.3% |
| 1,000 regular files, nested read      |  9.355 ms | 6.710 ms |          28.3% |
| Nested listing plus API JSON encoding | 10.068 ms | 7.358 ms |          26.9% |

The root read used **45.4% fewer allocations**, from 22,021 to 12,020 per operation.
These are medians of five alternating 500 ms batches per variant after a discarded
warm-up, using Go 1.27.4, the same fixture/dependencies, 2 CPUs, 2 GiB memory and
**GOMAXPROCS=2** on one Windows/WSL2 workstation. Nested fixtures and distinct file
contents are included. The test used warm Linux temporary storage, without
competing test/build jobs; unrelated workstation services remained running.

This does not replace the live HTTP/Wings comparison above or establish game/player
capacity. The next full benchmark must measure the released daemon under the same
complete workloads. See the [method and all eight cases](https://github.com/Aquadactyl/manta/blob/v1.3-beta/benchmarks/LISTING.md)
and [raw samples](https://github.com/Aquadactyl/manta/blob/v1.3-beta/benchmarks/results/listing-20261122.json).
